# Adding a Package

This guide walks through adding a new package to the Fromager database. By the end you will have a working database entry, know how to validate it, and have an example user configuration you can share with others.

## Overview

Every package in Fromager lives in a single YAML file under `database/<name>.yaml`. The root key is always `cheese:`. To add a package you need to:

1. Determine the package type and toolchain
2. Add the source URL(s)
3. Declare dependencies
4. Write the `build` section
5. Declare `properties` (flags other packages can consume)
6. Validate with `fgr selfcheck`
7. Write an example user configuration

---

## Step 1 — Determine type and toolchain

**Type** controls which cellar the package is installed into:

| Type | Cellar | When to use |
|---|---|---|
| `package` | user-specified | Regular libraries and applications |
| `compiler` | `cellars/compilers/` | GCC, LLVM, etc. |
| `mpi` | `cellars/mpis/` | OpenMPI, MPICH, MVAPICH, etc. |
| `vendor` | `cellars/vendors/` | Proprietary SDK bundles (NVHPC, Intel oneAPI) |
| `system` | `cellars/system/` | Reserved for `fgr init` bootstrap packages |

**Toolchain** tells Fromager how to build it:

| Toolchain | What it does |
|---|---|
| `cmake` | Runs `cmake ..` then `make` / `make install` |
| `autotools` | Runs `./configure` then `make` / `make install` |
| `makefile` | Runs `make` directly (no configure step) |
| `script` | Runs a custom script from `bin/` |

---

## Step 2 — Create the database file

Create `database/<name>.yaml`. The minimal skeleton looks like:

```yaml
cheese:
  name: <name>
  description: <one-line description>
  type: package
  toolchain: cmake   # or autotools / makefile / script

  source:
    type: tarball
    releases:
      - version: 1.0.0
        url: https://example.com/pkg-1.0.0.tar.gz

  dependencies:
    - zlib            # list direct dependencies only

  build:
    configurations:
      options: []     # fill in below

    stages:
      - target: ~     # default make target
      - target: install

  properties:
    ldflags:
      default: -L${<name>.prefix}/lib -Wl,-rpath,${<name>.prefix}/lib
    libs:
      default: -l<name>
    includes:
      default: -I${<name>.prefix}/include
```

---

## Step 3 — Write the `build.configurations.options` section

Options are passed as arguments to the configure/cmake command. There are two kinds:

- **Fixed options**: always set the same way; not shown to users.
- **User-configurable options**: marked `user_configurable: true`; appear in the template generated by `fgr template`.

### CMake example

```yaml
build:
  configurations:
    options:
      - name: -DCMAKE_INSTALL_PREFIX
        description: Installation prefix
        enabled_value:
          default: ${mylib.prefix}

      - name: -DCMAKE_C_COMPILER
        description: C compiler
        enabled_value:
          default: ${compiler.c}

      - name: -DCMAKE_CXX_COMPILER
        description: C++ compiler
        enabled_value:
          default: ${compiler.cxx}

      - name: -DCMAKE_C_FLAGS_RELEASE
        description: C compiler flags
        user_configurable: true
        enabled_value:
          default: -O3

      - name: -DMYLIB_ENABLE_TESTS
        description: Build tests
        user_configurable: true
        enabled:
          default: false
        enabled_format: -DMYLIB_ENABLE_TESTS=ON
        disabled_format: -DMYLIB_ENABLE_TESTS=OFF
```

### Autotools example

```yaml
build:
  configurations:
    options:
      - name: --prefix
        description: Installation prefix
        enabled_value:
          default: ${mylib.prefix}

      - name: CC
        description: C compiler
        enabled_value:
          default: ${compiler.c}

      - name: CFLAGS
        description: C compiler flags
        user_configurable: true
        enabled_value:
          default: -O3

      - name: --enable-mpi
        description: Enable MPI support
        user_configurable: true
        enabled:
          default: true
        requires: [mpi]
        enabled_value:
          default: ~
```

The `requires` field lists optional dependencies. If the user's recipe doesn't include any of the listed packages, the option is automatically disabled regardless of the `enabled` setting.

### Using conditions

Use `conditions` when an option's value depends on other options. Conditions are evaluated top-to-bottom; the first `set` action wins. `append` and `prepend` accumulate.

```yaml
- name: CC
  description: C compiler
  enabled_value:
    default: ${compiler.c}
    conditions:
      - condition: ${mylib.config.--enable-mpi} enabled
        action: set
        value: ${mpi.c}
```

See [Database Configuration Format](03-Database_Configuration_Format.md#conditions) for the full condition syntax.

## Step 4 — Handle optional external dependencies

If your package can use an external dependency from `config.yaml` (like `rdma-core` or `hcoll`), check for it with a condition:

```yaml
- name: --with-hcoll
  description: Build with HCOLL support
  user_configurable: true
  enabled:
    default: true
  enabled_value:
    default: ${hcoll.prefix}
  requires: [hcoll]
```

When `hcoll` is absent from the user's recipe (or set to `~` in `config.yaml`), Fromager automatically disables this option.

---

## Step 5 — Declare `properties`

Properties are what other packages consume when they depend on yours. At minimum, declare `ldflags`, `libs`, and `includes`:

```yaml
properties:
  ldflags:
    default: -L${mylib.prefix}/lib -Wl,-rpath,${mylib.prefix}/lib
  libs:
    default: -lmylib
  includes:
    default: -I${mylib.prefix}/include
```

For conditional properties (e.g. different flags when MPI is enabled):

```yaml
properties:
  ldflags:
    default: -L${mylib.prefix}/lib -Wl,-rpath,${mylib.prefix}/lib
    conditions:
      - condition: ${mylib.config.--enable-mpi} enabled
        action: append
        value: ${mpi.ldflags}
```

If your package is a **compiler** or **MPI implementation**, expose the compiler wrapper paths:

```yaml
properties:
  c: ${mylib.prefix}/bin/mpicc
  cxx: ${mylib.prefix}/bin/mpicxx
  fort: ${mylib.prefix}/bin/mpifort
  omp_flags: -fopenmp
```

By convention, MPI packages expose their properties under the `mpi.*` namespace, not their own name (e.g. `mpi.c` not `openmpi.c`). This is enforced by naming the properties section with the abstract package name. See [Abstract Configuration Format](04-Abstract_Configuration_Format.md) for how abstract packages work.

---

## Step 6 — Validate

Run the format verifier:

```bash
fgr selfcheck
```

Fix any reported errors before proceeding. Common mistakes:

- Missing required fields (`name`, `type`)
- Referencing a template variable that doesn't exist (e.g. `${foo.prefix}` when `foo` is not a dependency)
- A condition referencing an option that hasn't been defined yet in the same package

---

## Step 7 — Write an example user configuration

Create `examples/<name>.yaml` by generating a template and filling in reasonable defaults:

```bash
fgr template mylib > examples/mylib.yaml
```

Edit the generated file to set sensible versions and enable the most common options. This file serves as documentation and as a quick-start for users of your package.

## Complete Example: a CMake library with optional MPI support

Below is a complete database entry for a hypothetical library called `libfoo` that uses CMake and optionally supports MPI.

```yaml
cheese:
  name: libfoo
  description: Example high-performance library with optional MPI support
  type: package
  toolchain: cmake

  source:
    type: tarball
    releases:
      - version: 2.1.0
        url: https://example.com/libfoo/releases/libfoo-2.1.0.tar.gz
      - version: 2.0.3
        url: https://example.com/libfoo/releases/libfoo-2.0.3.tar.gz

  dependencies:
    - zlib

  build:
    configurations:
      options:
        - name: -DCMAKE_INSTALL_PREFIX
          description: Installation prefix
          enabled_value:
            default: ${libfoo.prefix}

        - name: -DCMAKE_BUILD_TYPE
          description: Build type
          enabled_value:
            default: Release

        - name: -DCMAKE_C_COMPILER
          description: C compiler
          enabled_value:
            default: ${compiler.c}
            conditions:
              - condition: ${libfoo.config.-DLIBFOO_ENABLE_MPI} enabled
                action: set
                value: ${mpi.c}

        - name: -DCMAKE_CXX_COMPILER
          description: C++ compiler
          enabled_value:
            default: ${compiler.cxx}
            conditions:
              - condition: ${libfoo.config.-DLIBFOO_ENABLE_MPI} enabled
                action: set
                value: ${mpi.cxx}

        - name: -DCMAKE_C_FLAGS_RELEASE
          description: C compiler flags
          user_configurable: true
          enabled_value:
            default: -O3

        - name: -DCMAKE_CXX_FLAGS_RELEASE
          description: C++ compiler flags
          user_configurable: true
          enabled_value:
            default: -O3

        - name: -DZLIB_ROOT
          description: Path to zlib installation
          enabled_value:
            default: ${zlib.prefix}

        - name: -DLIBFOO_ENABLE_MPI
          description: Enable MPI support
          user_configurable: true
          enabled:
            default: false
          requires: [mpi]
          enabled_format: -DLIBFOO_ENABLE_MPI=ON
          disabled_format: -DLIBFOO_ENABLE_MPI=OFF

    stages:
      - target: ~
        multithreaded: true
      - target: install

  properties:
    ldflags:
      default: -L${libfoo.prefix}/lib -Wl,-rpath,${libfoo.prefix}/lib
    libs:
      default: -lfoo
    includes:
      default: -I${libfoo.prefix}/include
```

And a matching `examples/libfoo.yaml`:

```yaml
cheese:
  libfoo:
    description: Example high-performance library with optional MPI support
    version: 2.1.0
    compiler: system
    build:
      configurations:
        options:
          - name: -DCMAKE_C_FLAGS_RELEASE
            description: C compiler flags
            enabled: true
            enabled_value: -O3
          - name: -DCMAKE_CXX_FLAGS_RELEASE
            description: C++ compiler flags
            enabled: true
            enabled_value: -O3
          - name: -DLIBFOO_ENABLE_MPI
            description: Enable MPI support
            enabled: false
            enabled_value: ~

  zlib:
    version: 1.3.1
    compiler: system

recipe:
  abstract_packages: {}
  dependencies:
    - zlib
    - libfoo
  targets:
    - libfoo
```

Install it:

```bash
fgr install -r examples/libfoo.yaml --cellar libfoo-nompi
```

## Style reference

For real-world examples of each pattern, look at these existing database entries:

| Pattern | File |
|---|---|
| CMake with many options | `database/geant4.yaml` |
| Autotools with MPI toggle | `database/hdf5.yaml` |
| Makefile (stage-level options) | `database/conquest.yaml` |
| MPI implementation | `database/openmpi.yaml` |
| Vendor package with submodules | `database/intel-oneapi.yaml` |
| Abstract package | `database/mpi.yaml` |
