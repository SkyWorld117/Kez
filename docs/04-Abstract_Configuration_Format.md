# Abstract Configuration Format

This document describes the abstract configuration format that serves as an interface for redirecting API calls to the appropriate concrete packages. The abstract configuration files are in YAML format and typically also follow the general structure of configuration files used in our system.

However, for the ease of use and configuration, there are more specific parsing rules applied to the abstract configuration files. These rules are designed to ensure that the abstract configuration can be easily translated into concrete package configurations.

## Structure of Abstract Configuration

In addition to the general structure defined in the [Database Configuration Format](03-Database_Configuration_Format.md), there is an entry `implementations` that specifies the concrete packages that implement the abstract package. The structure is as follows:

```yaml
cheese:
    name: <abstract_package_name>
    description: <abstract_package_description> # Optional, but recommended
    type: abstract
    implementations:
        - <concrete_package1>
        - <concrete_package2>
        - ...
```

Usually, there is no `source`, `build`, `dependencies`, `stages`, or `properties` sections in the abstract configuration, as these are defined in the concrete packages. By convention, the properties of the concrete packages will not use their own names but will use the abstract package name instead. This allows for a unified interface when calling the API.

For example, if the abstract package is `mpi`, the concrete packages like `openmpi` or `mpich` will define their properties as `mpi.c`, `mpi.cxx`, `mpi.fort`, etc. This way, the API can be called with the abstract package name, and it will automatically redirect to the appropriate concrete package.

## Parsing Rules

The implementations of the abstract packages are determined during the parsing process. Based on the task assigned by different commands, its behavior for choosing implementations may vary.

When generating a user configuration file, the system will ask the user to select a concrete implementation for each abstract package. However, if the user chooses to install a package via command line, the system will automatically select the implementation based on a [lookup table](../src/dependency_resolver/advisor.cpp). This lookup table offers decent suggestions for building a performant application.

Each abstract package will contain a property `.use-<concrete_package_name>` automatically set to `true` generated by the parser, where `<concrete_package_name>` is the name of the concrete package selected by the user. Respectively, the rest of the concrete packages will have this property set to `false`.
