# User Configuration Format

User configuration files are generated by Kez for precise control over a package's build
including its dependencies, build options, and properties. They are YAML files that the
user edits before installation.

## Workflow

The typical workflow for using a user configuration file is:

```bash
# 1. Generate a user configuration for one or more packages
kez uconf <package_name>... --save my-config.yaml

# 2. Edit the configuration file
$EDITOR my-config.yaml
#   - Change version, compiler per package
#   - Enable/disable patches
#   - Toggle build options on/off
#   - Modify option values
#   - Change environment variable values
#   - Note: do NOT add or remove entries from the structure

# 3. Install using the modified configuration
kez install --read my-config.yaml
```

Pre-built example configuration files live in the `archive/` directory
(e.g. `archive/sbrinz/openmpi.yaml`, `archive/sbrinz/hemelb-gpu.yaml`). These
demonstrate the full format including compiler selection per-package, abstract
package resolution, patch enabling, and build option overrides.

## Structure

The user configuration YAML has two top-level keys: `kez:` (per-package settings)
and `recipe:` (build plan metadata).

```yaml
kez:
  <package>:
    # Informational only; copied from the database recipe.
    description: <string>

    # First release in the source.releases list, or "latest" if absent.
    # For MPI packages: latest installed version in <KEZ_WORKDIR>/mpis/.
    # For Vendor packages: latest installed version in <KEZ_WORKDIR>/vendors/.
    # Use "name@/path/to/source" to override with a local source directory.
    version: <string>

    # Compiler spec in "<vendor>@<version>" or "system" format.
    # Generated for all package types except vendor and external.
    compiler: <string>             # e.g. "gcc@13.4.0", "system"

    # Present only when patches/<package>/ exists on disk.
    # Listed alphabetically; all disabled by default.
    patches:
      - name: <patch_filename>     # Filename from patches/<pkg>/
        enabled: false             # Set to true to apply via git apply

    build:                         # Present only if the recipe defines a build
                                   # AND the package is not a non-target
                                   # Compiler/Mpi type.
      configurations:
        environment:
          - name: <var_name>       # User-configurable env variables only
            description: <string>
            value: <default>
            requires:              # Present only if non-empty
              - <abstract_dep>

        options:
          - name: <option_name>
            description: <string>  # Present only if defined in recipe
            enabled: true|false
            enabled_value: <val>   # Null (~) for pure boolean flags
            disabled_value: <val>  # Present only if disabled_format exists
            requires:              # Present only if non-empty
              - <abstract_dep>

      stages:
        - target: <make_target>    # Null (~) for the toolchain default target
          configurations:
            options:
              - name: ...
                ...

  <dependency>:
    # Same structure as packages above, but typically less populated.
    ...

recipe:
  abstract_packages:               # Sorted alphabetically by abstract name
    <abstract_name>: <concrete_implementation>

  dependencies:                    # Ordered list of ALL non-system packages
    - <dep_1>                      # in the resolved dependency graph.
    - <dep_2>                      # Dependent-before-dependency order.
    - ...

  targets:                         # The original packages the user requested.
    - <target_package>             # Before abstract-package resolution.
```

Users should modify **values** of the entries (version, compiler, enabled, option
values, environment variable values) but should not add or remove entries unless
they understand the dependency graph. Adding a package to `kez:` without also
adding it to `recipe.dependencies` will cause a parse error.

## Field Reference

### `kez.<package>.description`

Optional. Copied from the database recipe's `description` field. Purely
informational — the parser ignores it.

### `kez.<package>.version`

Determined by the generation logic. A `version` field is emitted **only** when
the database recipe defines a `source` with at least one release.

| Package type | Version source |
|---|---|
| All types except MPI and Vendor | First entry in `source.releases` |
| `mpi` | Latest installed version in `<KEZ_WORKDIR>/mpis/<name>-*` |
| `vendor` | Latest installed version in `<KEZ_WORKDIR>/vendors/<name>-*` |

For MPI and Vendor types, the generated version is the **latest pre-existing
installation** (not the source release version). If no pre-existing installation
is found, the first release from the recipe is used as a fallback.

Users may override with a local source directory using the `name@/path` syntax
(see [Local Source Override](#local-source-override)). Setting `version: latest`
instructs the parser to use the latest release from the database recipe.

### `kez.<package>.compiler`

Generated for every package **except** those of type `Vendor` and `External`.
The value defaults to `settings.default_compiler` from `<KEZ_WORKDIR>/config.yaml`,
or `"system"` if no default is configured.

The compiler spec uses `<vendor>@<version>` format (e.g. `gcc@13.4.0`,
`nvhpc-compilers@26.5`). When `system` is specified — or when the version is
omitted — the compiler resolves to the platform's default system compiler
(`gcc@latest`).

### `kez.<package>.patches`

The generator scans `KEZ_HOME/patches/<package_name>/` for regular files.
Each discovered file becomes an entry (sorted alphabetically by filename)
with `enabled: false`. Users enable individual patches by setting `enabled: true`.

During parsing, each enabled patch is validated:
- The patch name must pass a path-traversal check (the filename component
  must equal the full name — no `/` or `..` allowed).
- The patch file must exist on disk at `KEZ_HOME/patches/<package>/<name>`.
- Enabled patches are applied to the unpacked source via `git apply <path>`.

### `kez.<package>.build`

The `build` section is **omitted** for packages of type `Compiler` or `Mpi`
**unless** the package is among the resolved targets. Resolved targets are the
packages the user originally requested, with abstract package names replaced by
their concrete implementations — so requesting an abstract target like `mpi`
that resolves to `openmpi` will include `openmpi`'s build section even though
it is an `mpi`-type package.

For all other types (`Package`, `System`, `Vendor`, `External`), the build
section is included whenever the recipe defines a `build` key.

### `build.configurations.environment`

Includes only environment variables that meet **all** of:
1. Marked `user_configurable: true` in the database recipe.
2. Every package in the variable's `requires` list is present in the resolved
   dependency set (with abstract-to-concrete mapping applied).

Each emitted variable includes `name`, optional `description`, `value` (the
recipe's default), and optional `requires`.

### `build.configurations.options`

Includes only build options that meet **all** of:
1. Marked `user_configurable: true` in the database recipe.
2. Every package in the option's `requires` list is satisfied.

Each emitted option includes `name`, optional `description`, `enabled` (boolean),
`enabled_value` (or `~` for pure boolean flags), optional `disabled_value`
(present only when the recipe defines a `disabled_format`), and optional
`requires`.

### `build.stages`

Only stages that carry a `configurations` block with at least one remaining
option or environment variable after filtering are emitted. Each stage contains:
- `target`: the make target name, or `~` (null YAML) for the toolchain default.
- `configurations`: the stage's filtered options and environment variables.

### `recipe.abstract_packages`

A map from abstract package names (e.g. `blas`, `mpi`, `lapack`) to the
concrete implementations selected during dependency resolution
(e.g. `intel-oneapi-mkl`, `openmpi`). Entries are sorted alphabetically by
abstract name.

The selection is made either:
- **Interactively** (the default for `kez uconf` and package-based
  `kez install`): the user is prompted to choose from each abstract package's
  `implementations` list.
- **Automatically** (with `--silence`): the heuristics advisor
  (`heuristics/advice.yaml`) selects the best implementation for the target
  architecture.

Users may change the implementation here before installation. The parser
validates that the chosen implementation exists in the database recipe's
`implementations` list. See [Abstract Package Resolution](#abstract-package-resolution)
for details on how this affects properties and conditions.

### `recipe.dependencies`

A YAML sequence of all non-system packages in the resolved dependency graph,
in **dependent-before-dependency** order (a package appears before the
packages it depends on). This order determines the build sequence.

Every entry in `recipe.dependencies` must have a corresponding entry in
`kez:` unless the dependency is of type `System`. Conversely, every package
in `kez:` must appear in `recipe.dependencies`.

### `recipe.targets`

A YAML sequence listing the original package names the user requested.
This is the input to `kez uconf <package>...` or `kez install <package>...`.
When abstract packages were among the targets, the corresponding concrete
implementation is used for build-section inclusion purposes.

## Validation Rules

When the parser processes a user configuration file, it enforces the following
rules and terminates with an error message on violations.

### Root Structure

| Rule | Error message |
|---|---|
| Root must contain a `kez:` map | `root must contain a kez map` |
| `recipe.dependencies` must be a YAML sequence | `recipe.dependencies must be a sequence` |
| `recipe.abstract_packages`, if present, must be a map | `recipe.abstract_packages must be a map` |

### Package Map Integrity

| Rule | Error message |
|---|---|
| Every key in `kez:` must appear in `recipe.dependencies` | `package '<name>' is absent from recipe.dependencies` |
| Every non-system dependency in `recipe.dependencies` must have a `kez:` entry | `non-system dependency '<name>' is absent from the kez map` |
| Each value in `kez:` must be a YAML map | `package '<name>' must be a map` |

### Abstract Package Validation

Each entry in `recipe.abstract_packages` is validated:
1. The key must name a package of type `abstract` in the database.
2. The value (the chosen implementation) must appear in that abstract
   package's `implementations` list.
3. If either check fails:
   `'<implementation>' does not implement abstract package '<name>'`

When valid, the parser also auto-generates `.use-<concrete>` properties for
every implementation (see [Abstract Package Resolution](#abstract-package-resolution)).

### Patch Validation

| Rule | Error message |
|---|---|
| `patches` must be a YAML sequence | `package patches must be a sequence` |
| Each patch entry must contain `name` and `enabled` fields | `patch entries must contain name and enabled fields` |
| Patch names must not contain path separators or `..` | `invalid patch name '<name>'` |
| Enabled patches must exist on disk at `patches/<pkg>/<name>` | `patch file does not exist: <path>` |

### Stage Validation

| Rule | Error message |
|---|---|
| `build.stages` must be a YAML sequence | `build.stages must be a sequence` |
| Each stage entry must be a YAML map | `build.stages entries must be maps` |

### Option and Environment Validation

When the parser encounters `user_configurable: true` options or environment
variables during plan generation, it requires corresponding user-provided
entries in the configuration file:

- For options: a named entry with an `enabled` field is required when the
  user includes a `build` section for the package. If the entry exists but
  `enabled` is missing and the option's `enabled` block in the database
  recipe has **no** conditions (so there is no fallback default), the
  parser reports:
  `"package '<name>' option '<name>' is missing its enabled value"`.
  If the database recipe does define conditions on the option's enabled
  state, the conditions are evaluated and their result supplies the
  enabled value — no error is raised.
- For environment variables: the named entry must exist in the user
  configuration when the user includes a `build` section. If the entry
  exists but its `value` field is absent or null, the value defaults
  to an empty string without error.

### Convergence

Conditional configuration values are resolved iteratively (up to
N+M+1 passes, where N and M are the number of options and environment
variables). If values do not stabilise:
`conditional configuration values did not converge`

## Generated Toolchain Options

For packages using the `autotools` or `cmake` toolchain, the generator
appends standard options to `build.configurations.options` even when the
database recipe does not explicitly declare them. These are ordinary
user-configurable options that the user can modify, just like any
recipe-declared option.

Options whose canonical key matches one already declared in the database
recipe are **not** duplicated — the recipe's definition takes precedence.

### Autotools

The following options are generated for every package with
`toolchain: autotools`:

| Option | Default value |
|---|---|
| `prefix` | `${<package>.prefix}` |
| `CC` | `${compiler.c}` (or `${mpi.c}` when MPI is a dependency) |
| `CXX` | `${compiler.cxx}` (or `${mpi.cxx}` when MPI is a dependency) |
| `FC` | `${compiler.fort}` (or `${mpi.fort}` when MPI is a dependency) |
| `CPPFLAGS` | `${<dep>.incflags}` for each active dependency |
| `CFLAGS` | `-O3 ${<dep>.incflags}` for each active dependency |
| `CXXFLAGS` | Same derivation as `CFLAGS` |
| `FCFLAGS` | Same derivation as `CFLAGS` |
| `LDFLAGS` | `${<dep>.ldflags}` for each active dependency |

**Compiler selection logic:** When `mpi` appears as an active dependency,
the MPI properties (`mpi.c`, `mpi.cxx`, `mpi.fort`) are preferred over the
base compiler properties (`compiler.c`, `compiler.cxx`, `compiler.fort`).

### CMake

The following options are generated for every package with
`toolchain: cmake`:

| Option | Default value |
|---|---|
| `CMAKE_INSTALL_PREFIX` | `${<package>.prefix}` |
| `CMAKE_BUILD_TYPE` | `Release` |
| `CMAKE_C_COMPILER` | `${compiler.c}` (or `${mpi.c}` when MPI is a dependency) |
| `CMAKE_CXX_COMPILER` | `${compiler.cxx}` (or `${mpi.cxx}` when MPI is a dependency) |
| `CMAKE_Fortran_COMPILER` | `${compiler.fort}` (or `${mpi.fort}` when MPI is a dependency) |
| `CMAKE_C_FLAGS` | `-O3 ${<dep>.incflags}` for each active dependency |
| `CMAKE_CXX_FLAGS` | Same derivation as `CMAKE_C_FLAGS` |
| `CMAKE_Fortran_FLAGS` | Same derivation as `CMAKE_C_FLAGS` |
| `CMAKE_CUDA_FLAGS` | Same derivation as `CMAKE_C_FLAGS` |
| `CMAKE_EXE_LINKER_FLAGS` | `${<dep>.ldflags} ${<dep>.libs}` for each active dependency |
| `CMAKE_SHARED_LINKER_FLAGS` | Same as `CMAKE_EXE_LINKER_FLAGS` |
| `CMAKE_MODULE_LINKER_FLAGS` | Same as `CMAKE_EXE_LINKER_FLAGS` |
| `CMAKE_BUILD_RPATH` | `${<dep>.lib}` paths joined with `;` for each active dependency |
| `CMAKE_INSTALL_RPATH` | Same as `CMAKE_BUILD_RPATH` |
| `CMAKE_PREFIX_PATH` | `${<dep>.prefix}` for each active dependency, joined with `;` |

### Default Value Derivation Rules

The template defaults are derived from the package's resolved dependencies:

**Include flags** (`-I` equivalents): Collected from every active dependency
that declares an `incflags` or `include` property. Each contributes
`${<dep>.incflags}`.

**Linker flags** (`-L` / `-Wl,...` equivalents): Collected from every active
dependency that declares `ldflags` or `lib` properties, plus the compiler's
own `ldflags` and the **package's own `ldflags`** (if defined). Each
contributes `${<dep>.ldflags}`.

**Libraries** (`-l` equivalents): Collected from every active dependency that
declares a `libs` property. Each contributes `${<dep>.libs}`.

**Library paths** (for RPATH): Collected from every active dependency that
declares a `lib` property, plus the compiler's `lib` and the package's own
`lib`. Paths are joined with `;` for CMake `-DCMAKE_*_RPATH`.

**Prefix paths** (for CMake `CMAKE_PREFIX_PATH`): Collected from every active
dependency. Each contributes `${<dep>.prefix}`. Paths are joined with `;`.

**Active dependencies** include:
- All of the package's direct dependencies that are satisfied.
- Dependencies required by any environment variable or build option
  (via `requires` fields) that are satisfied.

### What Is NOT Generated

- Autotools `LIBS` — Not generated by default. Only appears if declared
  explicitly in the database recipe.
- Options for `make` or generic (no toolchain) packages — these toolchains
  have no automatic options. Any options present were declared in the recipe.

## Abstract Package Resolution

### Purpose

Abstract packages serve as interfaces that redirect property lookups,
condition evaluations, and dependency resolution to the appropriate concrete
implementation. This allows recipes to declare dependencies like `mpi` or
`blas` without committing to a specific implementation at recipe-writing time.

### Selection

The mapping from abstract name to concrete implementation is recorded in
`recipe.abstract_packages`. The selection can originate from:

1. **User interaction** during `kez uconf` or package-based `kez install` — the
   user is prompted to choose from each abstract package's `implementations`
   list.
2. **Heuristics** with `--silence` — the advisor (`heuristics/advice.yaml`)
   selects automatically per architecture.
3. **Manual editing** — users may change values in the generated YAML before
   installation; the parser validates the change against the database.

### Property Namespace Sharing

By convention, concrete packages that implement an abstract interface define
their properties under the **abstract package's name** as the lookup key,
not their own name. This provides a unified API for dependents.

In practice, each concrete recipe declares simple property names (e.g. `c`,
`cxx`, `fort`), and the template system resolves abstract-name references
(e.g. `${mpi.c}`) by first mapping the abstract name to its concrete
implementation, then looking up the simple property on that config.

For example, the abstract `mpi` package is implemented by `openmpi` and
`mpich`. Template resolution works as follows:

| Template reference | When `mpi→openmpi` | When `mpi→mpich` |
|---|---|---|
| `${mpi.c}` | `${openmpi.prefix}/bin/mpicc` | `${mpich.prefix}/bin/mpicc` |
| `${mpi.cxx}` | `${openmpi.prefix}/bin/mpicxx` | `${mpich.prefix}/bin/mpicxx` |
| `${mpi.fort}` | `${openmpi.prefix}/bin/mpifort` | `${mpich.prefix}/bin/mpifort` |

A dependent package can reference `${mpi.cxx}` regardless of whether
`openmpi` or `mpich` was selected.

### The `.use-<concrete>` Mechanism

During parsing, the system auto-generates boolean named option states with the
pattern `<abstract_name>.use-<concrete_name>` for every implementation of each
abstract package. For example, if `mpi` is resolved to `openmpi`:

| Option state | Value |
|---|---|
| `mpi.use-openmpi` | `true` |
| `mpi.use-mpich` | `false` |

These properties are accessible in conditions throughout the configuration,
enabling packages to conditionalize options based on which concrete
implementation is active:

```yaml
conditions:
  - condition: ${mpi.use-mpich} true
    action: set
    value: -DMPICH_FOUND
```

### Validation

When the configuration is parsed, each entry in `recipe.abstract_packages`
is cross-checked against the database:
- The key must be a package of type `abstract`.
- The value must appear in that package's `implementations` list.
- Failure produces:
  `'<implementation>' does not implement abstract package '<abstract_name>'`

## Local Source Override

To test a package using a local source directory instead of fetching from a
remote:

```yaml
kez:
  my_package:
    description: My package description
    version: name@/path/to/local/source/directory
    build:
      configurations: <configurations_list>
      stages: <stages_list>
```

The `@` sign separates the package version (or name) from the local directory
path. The part before `@` is used for database lookups; the path after `@`
replaces the remote source with a `cp -a <path> source` command. This allows
developers to test uncommitted changes or custom builds without pushing to a
remote repository.
